# Rust port: deliberate divergences from the Python daemon

Every place where the Rust supervisor daemon (rust/crates/supervisor-daemon)
deliberately behaves differently from the Python daemon
(src/aleph/vm/supervisor/daemon.py and the modules it serves from). The Python
daemon remains the parity oracle for everything not listed here; anything else
that differs is a bug in the port. Dispositions: **keep** (intentional,
permanent), **fix-in-python-later** (the Python side has the bug and should
adopt the Rust behavior), **fix-in-rust** (a known Rust gap with a planned
increment) or **fix-in-both-later** (a shared wart neither side should keep).

| # | Divergence | Why | Disposition |
|---|------------|-----|-------------|
| 1 | Socket hardening: the Unix socket is bound under umask 0o077 and chmod 0700 afterwards as a backstop. Python binds with default permissions. | Day-one hardening (design doc section 3): only root, the agent's user, may connect; the socket is never observable with permissive modes. | keep |
| 2 | Identity-checked unlink at shutdown: the daemon records (st_dev, st_ino) of the socket it bound and only unlinks that inode. Python unlinks the path unconditionally and can remove a socket a newer daemon instance re-bound at the same path. | Same bug ported nowhere: fixed on the Rust side. The pre-bind stale-socket unlink stays unconditional, matching Python. | fix-in-python-later |
| 3 | No automatic .env loading. Configuration comes from the process environment; under systemd the unit's EnvironmentFile= provides it, for dev runs the explicit --env-file flag does. | Design doc section 6: implicit dotenv loading makes the effective configuration depend on the working directory. | keep |
| 4 | Empty-string ALEPH_VM_* path variables (SUPERVISOR_GRPC_SOCKET, PERSISTENT_VOLUMES_DIR) fall back to their defaults. Python turns "" into PosixPath('.') and then crashes or measures the current working directory. | An empty variable is an unset variable, not a request to operate on CWD. | keep |
| 5 | GPU inventory ordering is deterministic (lspci order, duplicates removed). Python builds the inventory via a set, so its order is nondeterministic. | The agent treats the inventory as a set; deterministic order costs nothing and makes byte-level comparisons and logs stable. | keep |
| 6 | JSON field whitespace in gpu_inventory_json / available_gpus_json / RecreateNetwork.summary_json is compact (serde_json default) where Python json.dumps uses ", " and ": " separators; summary_json keys also serialize alphabetically instead of insertion order. | Semantically identical payloads; consumers parse the JSON, nobody compares raw bytes. | keep |
| 7 | HostInfo proto fields the Python daemon never fills (cpu_architecture, cpu_vendor, cpu_model, frequencies, memory type, NUMA topology, the narrow gpus list, the SEV/TDX flags) stay at proto defaults in Rust too. | The proto promises more than either daemon delivers today; inventing values would diverge from the oracle. | keep |
| 8 | Ported warts kept bug-for-bug: a vfio-bound GPU from a non-whitelisted vendor aborts startup, and one lspci -nnk subprocess runs per PCI device before the class filter. | Parity first: fixing these on one side only would make conformance runs diverge. | fix-in-python-later |
| 9 | Increment staging (not a divergence, recorded so nobody is surprised): increment 3 landed settings.check() (the /dev/kvm, hypervisor-binary, socket-length and tool preconditions), the pool.setup() counterparts (store schema, forwarding sysctls, base nftables ruleset) and the boot-time nftables/ndppd reconcile (adoption step 5), plus the persistent lifecycle, port-forward mutations and RecreateNetwork. Still staged: ephemeral Firecracker programs, RunProgramCode, WatchEvents and StreamLogs (increment 4), the backup surface (increment 5), and the confidential mutations INCLUDING confidential CreateVm (increment 6), all answering UNIMPLEMENTED with the established trailer shape. | Each check and mutation lands with the increment that depends on it. | keep |
| 10 | Shutdown: the 5 second grace for in-flight RPCs matches Python's server.stop(grace=5). A second SIGTERM/SIGINT skips the grace, unlinks the socket (identity-checked) and exits immediately; Python has no second-signal path. | Dev convenience on the Rust side; harmless under systemd, which sends one SIGTERM. | keep |
| 11 | Stopped-but-defined VMs are reported. A controller config whose unit is not active stays in the world view and is served as STOPPED (stopped_at = the adoption instant, other stage timestamps 0), visible to GetVm/GetVmSpec/ListVms and counted in Health.vm_count. The restarted Python daemon instead stops and disables the unit and deletes the config at startup (load_persistent_executions + _cleanup_orphan_resources), which also destroys confidential VMs still awaiting their owner's initialization; it then answers NOT_FOUND for them. Duplicates get the same read-only treatment: when two ACTIVE configs claim the same vm_index, only the first (sorted file order) is adopted, mirroring Python's claimed_vm_ids guard; the others are not served (NOT_FOUND, absent from ListVms and vm_count), where Python also stops and destroys them. The Rust daemon does not adopt, but never destroys. DECIDED with increment 3: the destructive startup sweep (stop/disable dead controllers, delete their configs, tear down orphan chains and taps) is RETIRED, not ported. Adopted-stopped entries are real VMs: StartVm boots them back (the proto's documented StopVm/StartVm contract, which the restarted Python daemon breaks by deleting the definition) and DeleteVm releases them. Hidden VMs (failed adoption) keep their vm_index claims out of the allocator, and DeleteVm honors deletes of hidden VMs by stopping the untracked controller and removing its definition (the discard_failed_reattach port), so nothing becomes unmanageable. A create that failed to boot leaves a stopped-but-defined VM on the next Rust boot where restarted Python would have swept it. | A daemon that adopts must not destroy state; the sweep also destroyed confidential VMs awaiting owner initialization (fixed Python-side by #966 only for that case). | fix-in-python-later |
| 12 | An unparseable controller config file is logged and skipped (the VM is left alone and hidden, like a Python failed reattach). The Python daemon lets the pydantic ValidationError escape load_persistent_executions and aborts startup, crash-looping until an operator removes the file. | The 1.13.0 crash-loop lesson (PR #1016) applied to the one case Python still aborts on. | fix-in-python-later |
| 13 | Graceful degradation instead of startup aborts: with the D-Bus system bus unreachable the daemon still boots and logs, where the Python daemon dies in SystemDManager._connect after 3 attempts. A bus failure at adoption stamps NOTHING: unit states are unknown, so no VM gets stopped_at (or started_at, IPs, port forwards), and each VM's status defers to the live per-RPC unit queries until the bus answers ("bus unreachable" is distinguished from "bus answered, unit inactive" in the unit-state source's error taxonomy). Per-RPC bus failures degrade to all-inactive in both daemons. A per-VM IP-derivation failure at adoption (including invalid IPv4/IPv6 pool settings, which fail every running VM) HIDES the VM with a WARN, matching the restarted Python daemon, which parks failed reattaches in a retry queue and answers NOT_FOUND for them; the Python Network constructor additionally aborts the whole daemon on invalid pool settings, which the Rust daemon never does. D-Bus calls carry a Rust-only 5 second method timeout so a wedged (not just absent) bus also degrades instead of hanging boot or an RPC. Entries adopted under a bus outage carry no derived IPs, which entry 24 covers. | The daemon must boot in containers and stripped environments; a read-only reporter has no safe reason to refuse service, and a transient bus outage at boot must not permanently misreport every VM as stopped. | keep |
| 14 | GetHostInfo.available_gpus_json excludes every GPU referenced by a world-view controller config. Python originally never rebuilt VmExecution.gpus on reattach (adopted VMs' GPUs were reported available, inviting double-attachment); fixed by #1023, which rebuilds the GPU list for VMs adopted running. CLOSED with increment 3: VmInfo.gpus is rebuilt from the lspci inventory for VMs adopted running (inventory cards keep device_id and the hardware x-vga flag; unknown cards are recorded bare from the config, the `_rebuild_reattached_gpus` behavior) and set from the validated request at create. Adopted-stopped entries (which Python destroys, entry 11) report no attachments until StartVm. | Reporting an attached GPU as available invites double-attachment after every supervisor restart; the controller config knows the attachments. | done |
| 15 | GetLogs reads journald through a `journalctl -o json` subprocess; Python uses the native sd-journal binding. Same identifier matches (`vm-{hash}-stdout`/`-stderr`, OR-ed), same journal order, same microsecond timestamps. | No C dependency in the daemon, and the daemon sees exactly the view operators debug with. One subprocess per GetLogs call is fine for an operator-frequency RPC. | keep |
| 16 | GetLogs applies a Rust-only server cap of 10000 lines when max_lines is 0 (`journalctl -n 10000`, i.e. the LAST 10000 entries), and passes `-n max_lines` for tail requests, so the subprocess output is bounded at the source. The proto already documents max_lines 0 as "unlimited (subject to server cap)"; Python has no cap and buffers the whole journal history in memory. Head reads (from_tail=false with max_lines > 0) cannot use `-n` (it keeps the wrong end) and still slice after parsing, exactly like Python's `chunks[:max_lines]`. | Unbounded journal output is a memory DoS on the daemon; the Python side should adopt the same cap. Ordering semantics versus Python are unchanged. | fix-in-python-later |
| 17 | A negative vm_index hides the VM at adoption (IP derivation fails, the VM is skipped with a WARN, see entry 13). Python's `list(subnets)[vm_index]` instead serves the pool's LAST subnet for vm_index -1 (Python negative indexing), silently aliasing a valid subnet. | Deliberately NOT ported: serving the last subnet for a corrupt index is an accident of Python list indexing, not a design; two VMs could silently share a subnet. | keep |
| 18 | The cloud-init NoCloud seed is emitted as `#cloud-config` plus a JSON body (and a JSON network-config), where Python emits yaml.safe_dump output. JSON is a YAML subset, so cloud-init parses both into the same mapping; the parsed structures are asserted equal against the actual Python builders in tests/conformance/test_cloudinit_parity.py. The metadata file was already JSON in Python and stays byte-identical for ASCII hostnames; a non-ASCII hostname serializes as raw UTF-8 here where json.dumps escapes it as \uXXXX (same parsed value, entry 33). | Byte-matching PyYAML's line wrapping and quoting from Rust is fragile for zero benefit; the guest consumes the parsed mapping. | keep |
| 19 | settings.check() gating: the NETWORK_INTERFACE existence check and the ndppd availability check only apply when ALLOW_VM_NETWORKING is on; Python asserts both unconditionally (a daemon with networking disabled would still refuse to boot without a default route or ndppd). Everything else in the ported check() slice is as-is, including the /dev/kvm, hypervisor-binary and 108-byte socket-path aborts, plus (since the increment 3 review batch) the static-policy IPV6_SUBNET_PREFIX >= 124 abort of StaticIPv6Allocator. Deliberately NOT ported from conf.py:506-559: the CONNECTOR_URL scheme assert and the FAKE_DATA_* file asserts (agent-side settings the daemon does not model; they gate agent behavior, not the hypervisor surface) and the ENABLE_CONFIDENTIAL_COMPUTING block (sev-ctl path, SEV/SEV-ES CPU flags), which lands with the confidential mutations in increment 6. | A daemon that cannot create taps has no use for either; requiring them would break the container/CI boots increment 2 deliberately supports (entry 13's spirit). Agent-side and confidential checks land with the surface that needs them. | keep |
| 20 | Failing to enable the ip_forward/IPv6-forwarding sysctls at boot logs an ERROR and continues; the Python `Network.setup()` raises and kills the daemon (PermissionError without CAP_NET_ADMIN). The write gate itself is Python-identical: "1" is written only when the current value parses as int 0, so a host running with the sysctl at "2" (IPv6 forwarding with RA acceptance) is left alone, never clobbered to "1". An unparseable current value logs and continues where Python's int() would raise and kill the daemon. On a real node running as root with 0/1 values, behavior is identical. | Unprivileged and containerized boots (conformance CI, dev runs) must still serve; VMs on such a host lack connectivity either way. | keep |
| 21 | Mutations serialize on real locks: CreateVm under a daemon-wide creation lock (held across the boot wait, like Python's `creation_lock`) plus a per-VM lock that every other mutation (stop/start/reboot/reinstall/delete/port forwards) also takes, plus (since the increment 3 review batch) one coarse host-network lock over host-port allocation-through-persistence, tap/nftables setup and teardown, and RecreateNetwork's flush-and-rebuild. Lock order: creation_lock, then a vm_lock, then net_lock (innermost, never held across the systemd waits). Python only holds `creation_lock` and otherwise relies on event-loop interleaving, so two concurrent mutations of the same VM can interleave their steps there. | Blocking threads have no cooperative scheduling to lean on; serializing per VM (and serializing host-network mutations, which Python's event loop makes atomic for free) is strictly safer, and the agent serializes per VM anyway. | keep |
| 22 | initialize_nftables failure at boot: the daemon logs an ERROR and serves (a later RecreateNetwork can rebuild the base ruleset); the Python daemon dies inside `Network.setup()` and crash-loops until an operator fixes the host. Per-RPC nftables failures behave identically in both. | The graceful-degradation family (entries 13 and 20): a daemon that must adopt live VMs cannot refuse service over a rebuildable ruleset. | keep |
| 23 | No reattach retry loop: Python retries hidden VMs (failed reattaches) every REATTACH_RETRY_INTERVAL_SECONDS and can resurrect them once the transient cause clears; the Rust daemon hides them until the next daemon restart (or an explicit CreateVm, which re-adopts a live untracked controller). | Increment 3 scope; the retry loop is background machinery whose natural home is increment 4's event/watch plumbing. Revisit there. | keep (revisit in increment 4) |
| 24 | After a bus-unreachable boot (entry 13), adopted entries carry no derived IPs (entry.ipv4 is None) and RecreateNetwork skips them (the running filter requires an IP and nothing rederives one), so their chains cannot be restored by the RPC. Operational hazard: a node whose D-Bus was down at daemon boot cannot heal its VM chains through RecreateNetwork; it needs a daemon restart with the bus up. | Rederiving IPs lazily (from vm_index and vm_hash, both known) closes this; planned with increment 4. | fix-in-rust (increment 4) |
| 25 | Python's `is_service_active` (systemd.py:196-199) returns False for a unit that is active but not enabled (it checks enablement first): a CreateVm retry on such a VM answers INTERNAL (readopt refuses) and RecreateNetwork skips the VM. The Rust daemon reads the raw ActiveState, so active-but-disabled units count as running. | The enablement check in an activity probe is an accident; the raw ActiveState is the truth. | fix-in-python-later |
| 26 | Non-persistent QEMU CreateVm: refused up front (INTERNAL, zero side effects). Python executes the whole create and dies on `AlephQemuInstance.start()`'s NotImplementedError with an empty message, leaving the controller config, the cloud-init image and sometimes tap/chains behind. | The Python wart is destructive residue from a request that can never succeed; matching it would manufacture garbage on disk. | keep |
| 27 | ALLOW_VM_NETWORKING flipped off across a restart with persisted forwards: the Rust daemon adopts the VM and serves it RUNNING (with no IPs and no networking mutations); restarted Python hides it (the reattach dies rebuilding the tap). | A reachable-but-unnetworked VM is more honest than NOT_FOUND for a VM whose qemu still runs. | keep |
| 28 | A broken port-mapping store at adoption (unreadable database, corrupt table): the Rust daemon adopts the VM with zero forwards and a WARN; Python's reattach dies on the store read and hides the VM. | Same family as entry 27: the VM exists and runs; losing the forwards list is strictly less wrong than pretending the VM is gone. | keep |
| 29 | A mid-flight port-mutation failure (nft error halfway through an Add/RemovePortForward): Python leaves the partially-mutated mapped_ports dict visible; the Rust daemon writes the in-memory list only after the full diff succeeds, so readers see the pre-call snapshot. | Snapshot semantics are strictly safer; the store is only written on success in both daemons. | keep |
| 30 | CreateVm's readopt of a live untracked controller registers the world entry BEFORE restoring the network (a failure removes it again); Python registers the execution last. A concurrent GetVm can see the VM a moment earlier here. | The window is read-only and the failure path removes the entry; matching Python would need entry-less restore plumbing for no observable gain. | keep |
| 31 | D-Bus calls retry once on a fresh connection inside the same RPC (the cached connection may have died with a bus restart); Python's per-call failure propagates and only reconnects on the NEXT call. | One transparent retry absorbs bus restarts that Python surfaces as one spurious RPC failure. | keep |
| 32 | Crafted-state numeric/ruleset edges, grouped: a controller config whose mem_size_mb is a float string fails the whole config parse (Python's int() coercion raises the same way, but pydantic's error context differs); non-scalar nftables match predicates (dicts/lists where scalars are expected) are treated as non-matching instead of raising; host_port > 65535 in a crafted store row fails the bind probe (Python's socket.bind raises OverflowError -> caught as unavailable, same outcome); partially-overlapping nft output entries dedup by the superset rule identically. | Hostile-state edges where both daemons refuse service safely; byte-identical error text is not a goal (entry 33). | keep |
| 33 | Cosmetics, grouped: internal error message TEXTS may differ where no test pins them (the pinned ones are byte-identical); non-ASCII JSON string escaping (serde_json raw UTF-8 vs json.dumps \uXXXX, narrowing entry 18's metadata claim); the EXECUTION_LOG_ENABLED stop-time execution-record dump (_save_execution_data) is not ported (agent-side diagnostics of the pre-split layout); ndppd restart debounce coalescing may order the interface stanzas of one burst differently than Python's await interleaving; the 108-byte socket-path check counts bytes here and characters (len(str)) in Python, diverging only for non-ASCII EXECUTION_ROOT paths where the byte count is the kernel truth. | No consumer parses these surfaces; each would cost real complexity to match byte-for-byte. | keep |
| 34 | Joint hardening gap: neither daemon validates the SHAPE of vm_id (64-hex ItemHash). A crafted vm_id containing path separators reaches path joins (controller config, cloud-init seed, socket paths) in both daemons, so path traversal via vm_id is possible in both; the gRPC socket is root-only (0700), which is the current mitigation. Increment 3 deliberately did NOT add Rust-side validation (parity first: Python has none, and a stricter Rust daemon would refuse requests Python accepts). | Validate in both daemons together (one shared contract), with the agent's ItemHash typing as the model. | fix-in-both-later |
| 35 | Stop/teardown gating: Python creates the tap and chains for EVERY spec when networking is on (pool.create_vm_from_spec ignores internet_access) but gates teardown on `enable_networking` = spec.network.internet_access, so stopping an internet_access=false VM LEAKS its tap and chains for the life of the daemon (a restart heals it: the reattach rederives internet_access from the config's interface_name, which is always set). The Rust daemon gates teardown on the config's interface_name and cleans up. | The Python wart is a genuine resource leak (a dead VM's tap device and nftables chains linger); the Rust cleanup is correct. | fix-in-python-later |
| 36 | Shared wart, kept bug-for-bug: RebootVm on a STOPPED persistent VM restarts the controller unit without recreating the tap/chains and without clearing stopped_at/stopping_at or reloading the persisted port mappings (local.py:536-551; the Rust reboot stamps identically, pinned by a cargo test). The VM boots into a missing tap and keeps reporting STOPPED. | Both daemons should either refuse (the StartVm contract covers this) or run the full start path; fixing one side alone would diverge the conformance runs. | fix-in-both-later |
